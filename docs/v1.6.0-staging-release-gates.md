# v1.6.0 maintenance release acceptance — Ground Up excluded

**Status: NOT RELEASED.** This document is a checklist, not evidence that tests passed.
Never paste credentials or production database URLs into GitHub issues or workflow logs.

## 1. Environment isolation

Provision a completely disposable Supabase project with its *own* project ref,
SQL migrations and two synthetic player accounts, and a separate staging site
wired to this project. **Do not use production accounts, credits or inventory.**
The workflow safety script rejects known live Supabase and site URLs, but a
preview URL alone does not guarantee that its backend points to staging. A
person who controls the deployment must independently confirm the actual
backend project and environment-variable mappings.

Required GitHub Actions secrets for optional checks:
- STAGING_DATABASE_URL: connection with permission to inspect grants; disposable database only
- STAGING_SITE_URL: HTTPS staging application URL
- STAGING_SUPABASE_URL and STAGING_SUPABASE_ANON_KEY: synthetic project, not live
- STAGING_PLAYER_A_EMAIL, STAGING_PLAYER_A_PASSWORD
- STAGING_PLAYER_B_EMAIL, STAGING_PLAYER_B_PASSWORD

Optional PR acceptance activation:
- Set GitHub Actions variable `V16_STAGING_READ_ONLY_ENABLED` to `true` only after
  provisioning disposable staging and confirming the branch preview points to it.
  This runs real read-only RLS/RPC and two-account browser acceptance in the
  standard PR CI workflow. If absent, that job is **SKIPPED, NOT PASSED**.

Required Actions variable:\n- STAGING_ECONOMY_ITEM_SLUG: a disposable available, non-staff, non-boost
  cosmetic absent from Player A's inventory, priced within Player A's
  available synthetic credit balance. This fixture is **consumed** after
  a successful run. Reset the account/item in staging before rerunning.

## 2. Schema gate

Apply the complete migration chain to a *fresh staging database* with
migration history and rollback plan; confirm expected schema is 0083.
Do not apply one numbered SQL file to a live database in isolation.
Run the 'Staging database security acceptance' workflow with explicit
isolated-database confirmation and verify both SQL contract files pass.
This read-only SQL inspection validates grants and RLS enabled flags,
**not** actual data isolation with distinct client JWTs.

## 3. Account and economy gates

Run 'Staging two-account browser acceptance' using the two synthetic
logins. Validate a complete sign-in, friends, notifications and privacy
navigation for each separately authenticated user.

Then run 'Staging economy concurrency acceptance' with explicit
disposable write confirmation. It sends two simultaneous purchases
from separate authenticated sessions for the same account.
Required invariant: **exactly one success**, **exactly one price debit**,
and **exactly one inventory row**. A failing test may leave one successful
purchase committed: reset the synthetic fixture after investigation.

Separate remaining manual/automated acceptance:
- No anonymous reward or privileged RPC execution.
- RLS isolates rows across two accounts; no unauthorized read/update.
- Repeated gift, insufficient funds, simultaneous distinct senders,
  rollback and refunds leave correct ledger balances.
- Malformed and repeated score submissions cannot bypass reward limits;
  score authenticity is still unverified because gameplay scores originate
  from the browser.
- Password reset, MFA if configured, session expiry, blocking, reconnects,
  notifications and DM visibility across distinct accounts.

## 4. Mobile and accessibility gates

Require latest commit's CI, Chromium browser, Chromium mobile, WebKit mobile,
CodeQL, Halloween and axe accessibility workflows green. Test physical
iPhone Safari, Android Chrome, Chromebook-class hardware, keyboard and
VoiceOver/TalkBack. Verify rotation, overlays, zoom, CPU slowdown, reduced
motion, tab suspension, game restart, error recovery and gameplay scores.
Automated WebKit does not substitute for iPhone hardware.

## 5. Operations and privacy gates

Confirm latest Vercel deployment SHA and build status, all six intended
cron job executions **and their actual effects**, the Discord gateway
worker heartbeat and health, and a production rollback path. A green
preview is not proof of production availability.

Phase 7 optional analytics are **off by default**. Current helpers do
not constitute an analytics pipeline or permission to collect. Any
collection requires signed-off privacy/data inventory, consent/withdrawal
controls, deletion/retention, rights process and safeguards appropriate
for younger players. Do not enable or invent silent analytics.

## Release decision

Do not remove the draft flag or deploy until all critical acceptance
evidence has been recorded, signed off and tied to the *same commit SHA*
and its database migration version. If staging resources are absent,
mark the gate **BLOCKED/NOT RUN**, never **PASS**.
